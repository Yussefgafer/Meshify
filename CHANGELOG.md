V1.1.4
- [Fix] Discovery no longer shows a permanent orphan BLE peer — a scan-time synthetic ble_<hex> id (compressed 8-byte advertising UUID) is re-keyed to the real mesh UUID on the first GATT payload, but the discovery layer (driven only by DeviceDiscovered/DeviceLost) never received the swap, so the phantom row lingered forever and the real peer never appeared; the transport now emits DeviceLost(old) + DeviceDiscovered(new) at the re-key boundary, carrying the advertised name and RSSI via new BleScanner.getLastNameFor/getLastRssiFor helpers
- [Fix] BLE scan failures are no longer silent — BleScanner surfaces scan start/scan-fail errors via an onScanError callback that BleTransportImpl turns into TransportEvent.Error, so a missing BLUETOOTH_SCAN permission (or a dead scanner) is reported to the UI instead of leaving discovery blank
- [Fix] MULTI_PATH duplicate payloads no longer double-count — ChatRepositoryImpl deduplicates incoming payloads by payload.id before saving, so unread badges and message notifications fire once instead of twice when the same message arrives over both LAN and BLE
- [Fix] Returning to Discovery no longer blanks the peer list — TransportManager keeps a replayable discoveredPeers StateFlow (fed by DeviceDiscovered/DeviceLost) and DiscoveryViewModel seeds its peerMap from it on init; the merged event flow has replay=0 so a recreated ViewModel previously started empty
- [Fix] BLE failure is no longer invisible when LAN works — DiscoveryViewModel surfaces a non-fatal error (snackbar) instead of swallowing transport errors when peers are present, and BleStatusBottomSheet now reflects real BLE runtime state (BleTransportImpl.runtimeActive mirrored through TransportManager.bleRuntimeActive) instead of the bleEnabled preference, removing the ghost "Active"
- [Chore] BLE transport tidy-up — removed self ConnectionEstablished emit on start (polluted event stream with the local peer id), removed dead currentMtu field in BleGattClient (effectiveMtu is the real constraint), wrapped client.connect in try/catch in handleDeviceDiscovered so a missing BLUETOOTH_CONNECT surfaces as a TransportEvent.Error instead of killing the discovery collector, removed dead connectionLocks machinery from BleConnectionPool (zero external callers), aligned SettingsViewModel default TransportMode with the repository (MULTI_PATH), added BluetoothAdapter.isEnabled guard in BleGattServer.startServer (now throws IllegalStateException cleanly), cleared sendLocks in BleTransportImpl.stop to prevent per-peer mutex leak across stop/start cycles, and moved the "Unknown device" fallback to ble_unknown_device in en/ar strings
- [Fix] Discovery spinner is no longer fixed-duration — DiscoveryViewModel now clears isSearching the moment a DeviceDiscovered arrives (handleDeviceDiscovered) and the 2s delay in init{} survives only as a fallback when no peer ever shows up; refresh() continues to bound its own scan lifecycle so a pull-to-refresh never strands the spinner
- [Fix] Phantom BLE ConnectionLost no longer fires for a never-established peer — BleTransportImpl tracks establishedMacs (ConcurrentHashMap.newKeySet); handleClientConnected records the MAC only when a real ConnectionEstablished is emitted, and handleClientDisconnected gates the ConnectionLost emit on the address being in the set, so a server-side link-up that races ahead of alias resolution (and therefore emitted no ConnectionEstablished) no longer produces a phantom lost event. The re-key boundary in handleIncomingPayload also emits a ConnectionEstablished for the new meshId when the underlying MAC was already live, so subscribers see peer state transition cleanly across the synthetic-ble-id → real-mesh-UUID swap
- [Fix] BLE start no longer leaks scope + connectionPool on a failed GATT server service-add — BleTransportImpl.start() allocates a fresh CoroutineScope and BleConnectionPool before awaiting the GATT server's onServiceAdded callback; if the await returns false, stop()'s `!isStarted` guard short-circuits and the resources leak until process death. New private `tearDownPartialStart()` cancels and nulls the scope, clears and nulls the connection pool, and stops the GATT server; called from both the `!serverReady` branch and the outer `catch (e: Exception)` branch. A `catch (e: CancellationException) { throw e }` clause was added before the generic Exception catch so a mid-start coroutine cancellation is propagated instead of being misreported as "BLE start failed"
- [Fix] BLE reassembly timeout raised from 5s to 30s — the timeout is a sliding-window gap between consecutive chunks, so a single chunk delayed past 5s by BLE congestion or retransmits no longer strands and silently drops an otherwise-complete transfer; added BlePayloadSerializer round-trip unit tests (single/multi-chunk, in-order, out-of-order, per-peer isolation)
